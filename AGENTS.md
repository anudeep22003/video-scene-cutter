# Scene Slice & Download

## Collaboration and implementation principles

- Build evolutionarily: each change should leave a working application, even when its abilities are limited. Discuss a big-bang change with the user, including tradeoffs, before proceeding.
- Prefer simple, explicit code over cleverness, premature optimization, and unnecessary abstractions. Use clear, descriptive names and name nontrivial intermediate values.
- Add high-signal comments for surprising behavior, tricky control flow, and dependencies on side effects.
- Commit frequently in logically distinct units. Aim for fewer than 100 inserted lines; avoid exceeding 200 net insertions or touching more than five files in one commit where practical.
- Use commit prefixes `feat`, `fix`, `refactor`, or `chore`, an imperative title, and a bulleted body when complexity warrants it. Do not commit unrelated user changes.
- Use the underlying formatter rather than hand-formatting: Prettier for TypeScript and Ruff for Python. Provide a Makefile formatting target when adding formatting infrastructure.
- Run checks appropriate to the change. Test meaningful behavior and failure paths; avoid tests that merely mirror implementation.
- Explain obvious design errors and material risks, then let the user choose tradeoffs. Do not silently replace the chosen architecture or expand V1 scope.

## Product and stack

An unauthenticated application where users upload a video, discover scene boundaries, preview virtual cuts, request physical slicing, and receive an email linking to a ZIP and individual clips.

- `frontend/`: React + TypeScript SPA using Vite. Use TanStack Query for server state and polling.
- `backend/`: TypeScript Hono API deployed to AWS Lambda. Keep its local development server working.
- Database: Neon serverless PostgreSQL with Prisma as the application ORM.
- Storage: one private S3 bucket with prefix-based access and lifecycle rules.
- Processing: separate Lambda workers for scene detection and slicing/archiving, using PySceneDetect and FFmpeg/ffprobe.
- Email: transactional provider, not yet selected. Frontend hosting and infrastructure tooling are also undecided.
- Python is expected for PySceneDetect integration; frontend and API remain TypeScript. Worker runtime boundaries are an implementation decision to make explicitly.

Current repository status: React starter plus Hono HTTP/service/database-storage scaffold exist. Prisma schema, initial migration, PostgreSQL/Neon adapters, local Compose database, registration/status endpoints, and example tests are implemented; see `backend/README.md`. Python detection/slicing handlers and media tests exist in `workers/`; their S3/database contacts and dispatch remain unwired (see `workers/README.md`). TanStack Query, S3 integration, email, and cloud infrastructure remain planned. Inspect package scripts before running commands; the backend's existing deploy script targets a function named `hello`.

## V1 experience and constraints

1. Inspect the selected file locally, validate metadata, calculate a SHA-256 fingerprint, and initialize or recover an upload.
2. Upload directly to S3 using a short-lived signed upload grant. Use XMLHttpRequest for byte-level upload progress.
3. A raw-object creation event starts detection. The UI polls for status and cutpoints.
4. Preview each virtual scene using the original video and its start/end timestamps, before physical slicing.
5. Accept an email address and start asynchronous slicing. Processing must continue after the browser closes.
6. Email `/download/{video_id}` when the archive is ready. That page exposes archive and individual clip downloads.

- No accounts or login. A client-generated `session_id` lives in localStorage with an application-enforced one-hour TTL; localStorage has no built-in expiration.
- Proposed limits: 500 MB and 30 minutes; accepted declared MIME types are `video/mp4` and `video/quicktime`. Choose exact byte units in code and document them.
- Re-selecting the same file within an active session or refreshing must recover the same video and processing state.
- Poll approximately every two seconds while processing; stop on terminal states. Upload shows a percentage, detection shows `DETECTING`, and slicing shows completed/total clips. Polling is near-real-time.
- Browser preview boundaries are approximate; do not promise frame-accurate playback. MOV containers may contain codecs the browser cannot play; decide the unsupported-preview experience explicitly.

## State and persistence

Normal lifecycle: `UPLOADING -> DETECTING -> DETECTED -> SLICING -> COMPLETED`. Processing can end in `FAILED` with a safe, actionable error message.

Use conditional state updates to protect transitions from concurrent requests and duplicate events. Define retry/recovery behavior explicitly rather than resetting state indiscriminately.

### `videos`

- `id`: UUID primary key, generated by the database.
- `session_id`, `file_hash`: required text; unique together for session-scoped upload idempotency.
- `status`: constrained to the lifecycle values, initially `UPLOADING`; `error_message`: nullable text.
- `size_bytes`: required bigint; `duration_sec`: required floating point; `mime_type`: required text. Client values are provisional until verified by the worker.
- `raw_object_key`: required text; `zip_object_key`: nullable text.
- `detected_cuts`: nullable JSONB array of `{ index, start, end }` in seconds.
- `total_slices`, `slices_completed`: required integers, initially zero.
- `user_email`: nullable text, supplied when slicing is requested.
- `created_at`, `updated_at`: timezone-aware timestamps. Ensure updates actually maintain `updated_at`.

### `slices`

- `id`: UUID primary key; `video_id`: required foreign key to `videos`, cascading on database deletion.
- `slice_index`: required zero-based integer; unique with `video_id`.
- `object_key`: required text; `start_sec`, `end_sec`: required floating point; `size_bytes`: required bigint.
- `created_at`: timezone-aware timestamp.

Treat `slices` as the durable completion ledger. Count each successfully inserted slice once. Validate ordered, contiguous cutpoints with `0 <= start < end <= duration`, and keep progress between zero and `total_slices`.

Use Prisma migrations for schema changes. Select a Neon connection configuration and Prisma adapter compatible with the Lambda runtime; do not open unbounded database connections. Define JSON serialization for bigint fields explicitly.

## Storage and retention

| Object key                         | Intended retention |
| ---------------------------------- | ------------------ |
| `raw/{video_id}.mp4`               | About one day      |
| `slices/{video_id}/slice_0000.mp4` | About three days   |
| `exports/{video_id}/slices.zip`    | About three days   |

- These are the proposed keys; a `.mp4` suffix does not convert a QuickTime upload into MP4. Preserve or explicitly document the source container convention.
- Keep the bucket private. Issue short-lived signed URLs for upload, playback, and downloads; configure browser CORS for the required methods and headers.
- Filter processing events to `raw/` so worker output cannot recursively trigger detection.
- Retention is per object, not per video workflow. Raw input can disappear before delayed slicing; clips and archives can expire at different times.
- S3 lifecycle removes objects, not database records or email addresses. Define application expiry and database/PII retention separately; return unavailable/expired state without issuing broken download URLs.

## Worker behavior

Package PySceneDetect, its decoding dependencies, FFmpeg, and ffprobe at build time for the Lambda architecture/runtime. Do not install dependencies during each invocation. Pin versions and verify the deployed package can decode representative inputs.

### Detection worker

1. Claim the job idempotently and download the expected raw object into an invocation-specific temporary directory.
2. Verify actual object size and use ffprobe to validate streams, container, duration, and limits. Update provisional metadata with verified values.
3. Run PySceneDetect with `ContentDetector`, converting frame timecodes to ordered scene intervals in seconds.
4. Handle a video with no transitions as one full-length scene; verify the pinned version's `start_in_scene` behavior.
5. Persist cuts and total scene count, then conditionally transition to `DETECTED`.
6. Clean temporary files on normal/error exit. Hard timeouts may bypass cleanup; do not rely on `finally` for durable recovery.

### Slicing and archive worker

1. Claim the export job, load cuts and the existing slice ledger, and download the raw video.
2. For missing indices, cut one clip at a time, upload to its deterministic S3 key, then transactionally record completion and progress.
3. Use PySceneDetect's FFmpeg splitting facilities or an explicit FFmpeg invocation with H.264/AAC output. Verify timestamp semantics and representative output boundaries; prefer an explicit duration of `end - start` when constructing commands. Invoke processes with argument arrays, not shell interpolation.
4. Build the archive using `ZIP_STORED`. Completed clips can be downloaded from S3 to rebuild the archive on a retry; delete each temporary clip after adding it.
5. Upload the complete archive before publishing its key and transitioning to `COMPLETED`.
6. Send the completion email and track notification success separately from export success so delivery failures can be retried.
7. Clean only the invocation's own temporary directory. Never use broad cleanup patterns that could affect another job.

## Known design issues and decisions to revisit

These warnings preserve the user's Lambda-first, single-bucket V1. Present tradeoffs before introducing additional services or changing its architecture.

1. **AWS event mismatch.** `ObjectFinalized`, GCS URLs, and `X-Goog-Signature` in the source design are Google Cloud concepts. S3 uses `ObjectCreated` notifications delivered to supported AWS destinations, not a generic signed HTTP webhook. Choose direct Lambda delivery or an explicit adapter; events can repeat and arrive out of order. [AWS S3 events](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html), [delivery ordering](https://docs.aws.amazon.com/AmazonS3/latest/userguide/notification-how-to-event-types-and-destinations.html).
2. **Upload validation overclaim.** Signed headers can bind declared metadata; they cannot verify actual codecs or duration. For browser-enforced size ranges, consider presigned POST with `content-length-range`, which changes the upload response to include form fields. If retaining PUT, verify its exact signing/browser behavior and inspect actual size after upload. Worker validation remains mandatory. [S3 POST policy](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sigv4-HTTPPOSTConstructPolicy.html).
3. **Runtime feasibility.** Standard Lambda functions have a 15-minute invocation limit and configurable `/tmp` from 512 MB to 10,240 MB. Benchmark both detection and 30-minute exports; 500 MB input does not imply bounded processing time or output size. Checkpoints do not schedule continuation automatically. Decide bounded batches/reinvocation or another compute option if measurements require it. [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html).
4. **Archive growth and retries.** Deleting each clip does not bound disk usage: raw input plus the growing ZIP plus a clip must fit. Re-encoding can increase size, and every archive rebuild repeats download/assembly work. Slice checkpointing alone cannot rescue an archive that always exceeds runtime or disk capacity.
5. **Checkpoint counter bug.** `INSERT ... ON CONFLICT DO NOTHING` followed by an unconditional increment overcounts on duplicate execution, even inside one transaction. Increment only when a row was inserted, or derive progress from the ledger. A composite unique constraint provides indexed lookup, not a guarantee of O(1) complexity.
6. **Dispatch and concurrency gaps.** A state update followed by invocation can fail between those operations, leaving a stuck job; duplicate workers can also race. Before claiming fault tolerance, define durable dispatch/reconciliation, job ownership, stale-job recovery, retry limits, and terminal failure handling. Conditional status updates alone do not solve the dispatch gap.
7. **Anonymous access and abuse.** A client session ID is not authentication. Decide whether possession of an unguessable video ID deliberately grants read/export access, or introduce separate capability tokens. Define who may set the recipient email. Public upload, compute, and email endpoints need explicit rate/cost limits before public deployment.
8. **Retention precision.** S3 lifecycle rounds age-based expiration to UTC day boundaries and deletes asynchronously; it cannot promise exact 24/72-hour deletion. Application expiry and DB cleanup need their own policy. [S3 lifecycle timing](https://docs.aws.amazon.com/AmazonS3/latest/userguide/intro-lifecycle-rules.html), [expiration delays](https://docs.aws.amazon.com/AmazonS3/latest/userguide/how-to-set-lifecycle-configuration-intro.html).
9. **Fingerprint semantics.** Define whether SHA-256 covers all bytes or a sampled composite. A sampled hash can collide for different files; a full-file hash is not necessarily fast or memory-cheap. Session/file uniqueness does not prevent an unexpired upload URL from overwriting input; bind processing to a stable object identity or explicitly prevent replacement.
10. **Email is a separate side effect.** A crash after marking `COMPLETED` can lose the email; retrying after sending can duplicate it. Define durable notification state and provider idempotency where available. Do not turn a successful export into `FAILED` solely because email delivery failed.
